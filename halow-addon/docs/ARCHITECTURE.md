# HaLow access point add-on: architecture and module contracts

> This document is the engineering contract between the subsystems of the add-on. Anything marked *unverified* has been implemented and tested off-device only. Radio, networking and status-page behavior was exercised on one Home Assistant Green running Home Assistant OS 18.4, with the clients used in testing; evidence is limited to that device.

## 1. What the add-on is made of

One Home Assistant add-on whose container runs three cooperating parts under s6:

| Part | Runs as | Does |
|---|---|---|
| `manager` (`rootfs/etc/services.d/manager`) | root, the add-on's full grant | The only writer of host state and of the status snapshot. Reconciles the host, checks compatibility, loads the driver and firmware, starts the access point and the networking, supervises them, and rolls back what it changed. Stays alive in an *attention required* state when something is wrong, so the status page can explain it. |
| access point and networking services | children of `manager` | `hostapd_s1g`, `dnsmasq`, the bridge backend (address, DHCP, firewall chains, NAT). |
| `status` (`rootfs/etc/services.d/status`) | launcher as root, server as a non-root user with no capabilities | A small GET-only HTTP service that renders the Ingress page and `/status.json`, `/diagnostics` (redacted) and `/health` from the snapshot the manager writes. It has no control endpoints. |

## 2. Rules for every contributor

1. **Libraries** live in `rootfs/usr/lib/halow/*.sh`. They define functions and constants only and never run anything when sourced. They are re-sourceable (plain assignments, `declare -gA` for arrays, no `readonly`), tolerate being sourced inside a function, and are safe under `set -o errexit -o errtrace -o nounset -o pipefail -o inherit_errexit` (capture a status with `if cmd; then rc=0; else rc=$?; fi`; never `local x="$(cmd)"` for a status that matters; never `cmd | grep -q`, `| head`, `| sed -n '…q'`: a guard test fails the suite on these).
2. **Prefix** every function `halow_<module>_`; a module's private helpers start with `_halow_<module>_`.
3. **No JSON tools in the product code.** Build JSON in bash with the escape helper from `state.sh`; the status service is Python (standard library only). Tests validate JSON with `python3`.
4. **Secrets.** The passphrase never appears on a command line, in a log line, in the snapshot, in diagnostics, or in a file outside `HALOW_RUN_DIR` (mode 0600, written under `umask 077`). Rendered access-point configuration lives only in `HALOW_RUN_DIR`, which is memory-backed because the manager mounts a tmpfs on it before anything is written there (§ 4, step 0). The Supervisor token is readable by root only: `rootfs/etc/cont-init.d/00-restrict-container-environment` runs as root before any service and makes s6-overlay's saved container environment (`/run/s6/container_environment`) mode 0700 with its files 0600, verifies that, and fails (s6-overlay then stops the container, `S6_BEHAVIOUR_IF_STAGE2_FAILS=2`) when it cannot; the status launcher passes no token on and refuses to start the server if the token is readable by the server's user.
5. **Ownership markers** (`ownership.sh`: `halow_own_mark/check/get/clear/list`) are written **before** the change they describe, cleared only after the undo is confirmed, and a key is never cleared on a guess. Markers are hints; the host is the truth: every undo also recognises its resource from the host itself (named firewall chains, the bridge name, processes by identity).
6. **External commands** are called by name so the tests can put fakes first on `PATH`; where a binary is selectable it is overridable by an environment variable (`HALOW_IPTABLES`, `HALOW_IP6TABLES`, `HALOW_IP`, `HALOW_BRIDGE_CMD`, `HALOW_HOSTAPD_CLI`, `HALOW_NFT` …). `HALOW_NFT` is only a read-only probe used to decide whether the add-on itself created the empty `INPUT` base chain that iptables-nft makes implicitly (see firewall.sh); the image carries the exactly pinned `nftables` package (`nft` 1.1.5, used only as `nft list chain`; the chain removal itself stays with iptables/ip6tables), and where `nft` is missing or cannot read the chain no claim is made and the chain is left (fail closed). Known limits of that cleanup: only `INPUT` of the `filter` table is handled (not an empty table the host never had), and a host that creates an identical empty `INPUT` chain in the sub-second window between the absence probe and the first insertion would have it removed at rollback (the host's rules are never removed: the kernel refuses to delete a chain that holds rules).
7. **Product text must be self-contained.** Files under `halow-addon/` (code, comments, tests, documents) must not refer to the private project record or its governance: no decision or architecture-record identifiers, no milestone or phase labels, no review or tier language, no personal names or paths. Say "validated on the target device" or "awaiting live validation". The boundary test enforces this.
8. **Protected libraries.** `module_load.sh`, `nm_unmanaged.sh`, `firmware.sh` and `common.sh` are the privileged host mechanisms and are unchanged by design (an equivalence test compares them with the reference); `checksum.sh`, `iface_detect.sh`, `hostapd_config.sh`, `network_backend.sh`, `backend_routed_nat.sh`, `health.sh` and `ownership.sh` are shared foundations. Behaviour that one of them lacks is added in the calling module (for example a preflight in the manager), not by editing them; `constants.sh` holds only shared values.
9. **Tests.** Each subsystem ships `tests/test_<area>.sh` suites that run through `tests/run_tests.sh` with `tests/test_helpers.sh` (`halow_test_setup` sources every library and redirects every path to a temp directory). Add helpers in your own `tests/helpers_<area>.sh`, fakes in `tests/fakes/`. A test must be able to fail: assert state and effects, not only log text. While other subsystems are being built concurrently, the full suite may be red in areas you do not own; keep your own suites and `bash -n` green and report anything you see.

## 4. Manager start sequence (one attempt)

`manager.sh` runs these steps in order; each step names the module that provides it and the catalogue error it raises. Any failure rolls back exactly what was recorded, sets the error, and (for recoverable errors) waits with bounded backoff before a **full** new attempt.

0. **Run directory and preflight (once per manager process, before anything is written).** If `HALOW_RUN_DIR` is not already a tmpfs (read from `HALOW_PROC_MOUNTS`), mount one: `mount -t tmpfs -o mode=0755,size=$HALOW_RUN_TMPFS_SIZE,nosuid,nodev,noexec tmpfs "$HALOW_RUN_DIR"` (`mount` called by name). The mount lives in the container's own mount namespace and disappears with the container. Then create `HALOW_RUN_READY_FILE`; the status launcher waits for it. A failed mount is `HOST_STATE_FAILED`: fail closed, nothing is rendered. A preflight also fails closed (`HOST_STATE_FAILED`) when `/proc/[0-9]*` does not expand to at least the manager's own pid, since every process-identity scan would otherwise report "absent". (`manager.sh`)
1. **Refusal check.** A persisted refusal marker (`ROLLBACK_INCOMPLETE` seen earlier) allows only rollback retries, never new mutation. (`reconcile.sh`)
2. **Reconcile first.** Inspect the host and the markers; compare `boot_id`; undo residue (firewall chains, bridge, processes, sentinel, modules this add-on loaded) by recognising it from the host. Unconfirmed residue → `ROLLBACK_INCOMPLETE` and the refusal marker. (`reconcile.sh`)
3. **Options.** Load and validate the options: `CONFIG_INVALID` naming the option; `REGION_UNVALIDATED`. (`options.sh`, `radio.sh`, `validate.sh`, `allowlist.sh`, `uplink.sh`)
4. **Compatibility guard — before any host change other than the run-directory tmpfs and step 2's undo of the add-on's own residue.** Exact host-module identity (§ 5.4): `UNSUPPORTED_KERNEL`; artifact checksums → `FIRMWARE_INVALID`. (`guard.sh`, `checksum.sh`)
5. **Adapter.** Exactly one supported adapter: `NO_ADAPTER` / `MULTIPLE_ADAPTERS` (recoverable). (`adapter.sh`)
6. **Firewall filter chains** populated and hooked **before** the bridge, hostapd or DHCP exist, including (both families) catch-all drops for `-i <radio interface>+` in INPUT and FORWARD, so a radio or per-station interface that is not (yet) a bridge port is never ungoverned. (`firewall.sh`)
7. **Driver and firmware.** Place firmware, set the host firmware search path, load `dot11ah` (channelisation scheme from the radio profile) and `morse`, confirm the board file matched, restore the search path. The board file is confirmed only from the kernel-log records written after a marker (the newest record, taken immediately before the `morse` load; never a line count, which the kernel log ring defeats by evicting old lines) and only by the driver's own `Loaded BCF from <name>, size <n>, crc32 <x>` record, which must name the placed board file with its size and CRC-32; the generic "Driver loaded" record is not evidence, and a lost marker, unreadable log or missing record fails closed. The check depends on the driver's exact `morse micro driver registration` anchor line and `Loaded BCF from <path>, size N, crc32 0x..` record; a driver build that words them differently fails closed (`FIRMWARE_INVALID`, with the reason in the detail) until the check is updated. Before each module load the manager records an intent marker `module_intent_<name>` holding the modules already present; reconcile treats a present module with an intent marker (and no completed marker) as this add-on's own and unloads it, and `libarc4` pulled in by `mac80211` is covered by the before/after comparison. A failed restore of the firmware search path is recorded in diagnostics and shown. `MODULE_LOAD_FAILED` / `HOST_STATE_FAILED` / `FIRMWARE_INVALID`. (existing `module_load.sh`, `firmware.sh`)
8. **Derive the interface** of the adapter from its sysfs tree; mark it unmanaged in NetworkManager (strict). `NM_CHECK_FAILED`. (`adapter.sh`, `nm_unmanaged.sh`)
9. **Bridge.** Create the bridge (marker first, pinned MAC, STP off, up) and mark it unmanaged (tolerant of an already-excluded device). Switch IPv6 off on the radio interface and the bridge with `halow_ipv6_disable`; if neither that nor the IPv6 chains can be verified, `BACKEND_FAILED` with a detail naming IPv6. (`bridge.sh`, `nm_unmanaged.sh`, `ipv6.sh`)
10. **Access point.** Render the configuration from the radio profile (`radio.sh`), start `hostapd_s1g`. In automatic mode the configuration asks hostapd for automatic channel selection; before the first automatic launch the manager waits `HALOW_ACS_PRESTART_SETTLE_S` (3 s) after the radio is released from the host's network manager and supplicant, and relaunches hostapd up to `HALOW_ACS_SURVEY_RETRIES` (2) more times after `HALOW_ACS_SURVEY_SETTLE_S` (3 s) only when hostapd's own log carries the empty-survey message (every other failure and manual mode follow the old path; both are defensive timing measures, not a root-cause fix, and the first failed launch of each attempt is recorded by the failure recorder, with the retries bounded at 5 and the waits at 30 s); the manager waits for its completion, failure or `HALOW_ACS_TIMEOUT_S`. On failure or timeout it stops hostapd, renders the **fallback** channel for the chosen bandwidth and starts again, records the channel source as `fallback`, and raises the `RADIO_AUTO_FALLBACK` advisory. `AP_START_FAILED`. (`radio.sh`, `hostapd_config.sh`)
    Right after hostapd starts the manager runs `halow_bridge_enforce_isolation` once (hostapd itself adds per-station ports to the bridge). The automatic-selection wait passes the selected bandwidth to `halow_radio_acs_wait`, so a completion on a channel of another width counts as a failure and the fallback is used; the wait calls the manager's heartbeat through `HALOW_RADIO_POLL_HOOK`, and every other long wait flushes a heartbeat too.
11. **Effective radio values** are read from the running access point and checked against the selected profile. A readable status that disagrees with the profile is `RADIO_MISMATCH`. A status that cannot be read (`HALOW_EFF_STATE=unavailable`) is not a mismatch: the access point stays up, `effective` stays unset, a diagnostics note is recorded and the page shows the configured values as requested only. (`radio.sh`)
12. **Backend.** Configure and attach the bridge backend: the radio interface is isolated as a bridge port when the backend attaches; gateway address on the bridge, dnsmasq bound to the bridge, NAT chain installed **last**. A NetworkManager failure inside the backend (`HALOW_BB_FAIL_KIND=nm`) is `NM_CHECK_FAILED`; other backend failures are `BACKEND_FAILED`; `UPLINK_UNAVAILABLE`. (`backend_bridge.sh`, `dnsmasq.sh`, `firewall.sh`)
13. **Operating.** State `operating`; supervise: station events and `all_sta` polling, hostapd and dnsmasq liveness, adapter presence, uplink change, `halow_bridge_enforce_isolation` on every tick, firewall jump re-assertion (a `halow_fw_reassert` failure is `BACKEND_FAILED`: fail closed and roll back), backend health, status-service liveness, heartbeat. Status liveness (`_halow_mgr_status_check`; **no request is made to the status listener**: it accepts only the Ingress proxy and drops every other peer, the manager's own address included, so a probe over the network could only be refused): about every `HALOW_MGR_STATUS_CHECK_S` (30 s) the manager evaluates four conditions, all without a connection. (1) `$HALOW_S6_SVSTAT -o up,pid $HALOW_S6_STATUS_SERVICE_DIR` prints exactly `true N` (s6 2.15.1.0 as shipped in the image prints `true <pid>` for a service that is up, also while it is wanted down, and `false -1` for one that is down, never started or killed; with no supervisor it prints `s6-svstat: fatal: unable to read status for <dir>: s6-supervise not running` and exits 1; the error text is not logged; the human-readable form `up (pid N pgid N) 2 seconds, ...` is not parsed because it differs between s6 releases and the old `up (pid N) ...` form is not accepted; the real outputs of every state are kept in `tests/fixtures/s6-svstat-real.txt`, which every fake of s6-svstat in the tests is built from), and the process `N` is the status server: `/proc/N/cmdline` holds the server program as one whole argument and `--port <recorded port>` as consecutive arguments, and `/proc/N/status` shows the status user as real and effective uid (a reused pid, another program, another port or a server that kept root fail). (2) The port in `HALOW_STATUS_PORT_FILE` (digits only, 1 to 65535, at most 16 bytes read) is in LISTEN state (`0A`, remote `00000000:0000`) on `HALOW_STATUS_BIND` in the kernel's IPv4 TCP table `HALOW_PROC_NET_TCP`, owned by the status user: the table is read (a kernel file: it cannot be replaced by a FIFO), never connected to, with at most `HALOW_MGR_TCP_TABLE_MAX_BYTES` and `HALOW_MGR_TCP_TABLE_MAX_LINES` considered (listeners come first in the kernel's table); address and port are compared in the kernel's notation (address bytes reversed, port big-endian, upper-case hex), lines that lack any field are ignored, and more than one listener on the address and port is ambiguous and fails. Only the IPv4 table applies because the status server binds the IPv4 bridge gateway (the server also supports an IPv6 bind; a bind address that is not dotted-quad IPv4 fails this check). (3) The counter file `HALOW_STATUS_HEARTBEAT_FILE` (its directory belongs to the status user, who could swap the file for a FIFO or a link between the type check and the read) is a regular file, not a link, and is read by a bounded, time-limited command (`$HALOW_TIMEOUT_CMD $HALOW_MGR_FILE_READ_TIMEOUT_S head -c <limit>`, 2 s: a FIFO makes the check fail, never hangs the manager; the port file is read the same way) of at most `HALOW_MGR_HEARTBEAT_MAX_BYTES` (32) bytes holding 1 to 20 digits and an optional newline; anything else fails. Its value is never logged. (4) The value differs from the previous reading for the same pid. The first reading for a pid, and the first after any failure of (1) to (3) or after a restart request, is only a baseline (counts as healthy); a reading equal to the previous one fails; a different one, lower or higher (the counter starts again at 1 when the status service restarts), counts as changed. A failed check increments the consecutive-failure count and logs `manager: the status service did not answer (n of m): <fixed reason>`; `HALOW_MGR_STATUS_FAILS_MAX` (2) consecutive failures ask s6 to restart the service once (`$HALOW_S6_SVC -r $HALOW_S6_STATUS_SERVICE_DIR`), reset the count and the baseline, and record `status_service`; a success resets the count. With the nominal 30 s ticks and the two-failure limit a hung accept loop is restarted about 60 to 90 s after it hangs (about 60 s when it hangs right after a check, about 90 s when it hangs just before one, because that check can still see a value written before the hang), plus the time s6 takes to restart the service; a dead or wrong process 30 to 60 s after. Start-up window: the service can be up with its port recorded before it listens or has written its first value; that is at most one failed check, cleared by the next success. The check returns 0 and never raises attention (the status page is not the access point). A counter file left by an earlier run cannot stand in for a new one: the launcher removes it before starting the server, the server writes its first value before accepting a connection, and a new pid starts a new baseline. A missing file during start-up is an ordinary failed check, so the 30 s interval and the failure limit of 2 are the start-up grace. `AP_DIED`, `UPLINK_UNAVAILABLE`, `INTERNAL_ERROR`. (`manager.sh`, `stations.sh`)

**Stop.** The TERM/INT handler only records that a stop is pending; the main loop acts on it at its own check points (every wait is interruptible) and runs the rollback outside the signal handler, with a normal `IFS`.

**Rollback order** (`rollback.sh`): backend (DHCP, NAT chain and jump) → NetworkManager marks of station interfaces → hostapd → bridge → NetworkManager marks of bridge and parent → IPv6 switches restored (`halow_ipv6_restore_all`) → remaining firewall jumps then chains → modules → firmware search path → firmware files. Each step confirmed; anything unconfirmed is reported and the function returns non-zero.

**Retry policy** (`lifecycle.sh`): recoverable errors (`NO_ADAPTER`, `MULTIPLE_ADAPTERS`, `UPLINK_UNAVAILABLE`) retry forever with backoff 5 s doubling to a 120 s cap; `AP_START_FAILED` and `AP_DIED` retry at most 3 consecutive attempts, then stay in `attention required`; configuration and compatibility errors never retry (the action text says change the option and restart, or update the add-on).

## 5. Module contracts

Return codes: 0 success; non-zero as stated. "prints" means stdout.

Catalogue: `NO_ADAPTER MULTIPLE_ADAPTERS UNSUPPORTED_KERNEL REGION_UNVALIDATED CONFIG_INVALID FIRMWARE_INVALID MODULE_LOAD_FAILED HOST_STATE_FAILED AP_START_FAILED AP_DIED BACKEND_FAILED NM_CHECK_FAILED UPLINK_UNAVAILABLE ROLLBACK_INCOMPLETE STATUS_STALE RADIO_MISMATCH INTERNAL_ERROR`, plus the **advisory** `RADIO_AUTO_FALLBACK` (the access point is up; it is not an attention state).

**Snapshot** (`status.json`, schema 2; schema 1 had `{mac, online, ip, last_seen, kind}` per station and is refused by the status service):

```json
{ "schema": 2, "updated_at": 0, "started_at": 0, "boot_id": "",
  "overall": "starting|operating|attention",
  "attention": null,
  "advisory": null,
  "region": "AU",
  "radio": { "mode": "automatic|manual",
             "requested": { "bandwidth_mhz": 1, "channel": null },
             "effective": null,
             "last_applied": null },
  "adapter": { "present": false, "interface": "" },
  "backend": { "applied": false, "bridge": "", "subnet": "", "gateway": "" },
  "stations": [],
  "diagnostics": {} }
```

`attention` is `null` or `{code, summary, action, detail, since, host_clean, retryable}`; `advisory` is `null` or `{code, summary, action, since}`; `effective` and `last_applied` are `null` or `{frequency_khz, channel, bandwidth_mhz, source, applied_at, validation, fallback_validated}`; a station is `{mac, online, online_source, kind, connected_since, state_changed_at, ips, devices, devices_omitted}`, a device is `{mac, ips}` and an address entry is `{ip, source, conflict}`. Fields: `mac` is the radio MAC hostapd reports (one primary row per HaLow station); `online` is the authorised state; `online_source` is `hostapd` or `log`; `kind` is `ordinary` or `wds`; `connected_since` is the epoch of the latest AP-STA-CONNECTED after the last disconnect (`null` unless online and known); `state_changed_at` is the epoch of the latest connect or disconnect event (it says nothing about traffic); `ips` are the addresses of the station's own MAC; `devices` are the downstream devices (zero or more, WDS stations only); `devices_omitted` is how many were left out by the bounds (16 devices per station and 4 addresses per MAC in `stations.sh`, 32 per station, 8 per MAC and 2048 devices in all in `state.sh`); `source` is `dhcp`, `neighbour` or `dhcp+neighbour`; `conflict` is true when more than one MAC claims that address. Behaviour: devices are the MACs learned on the station's own port in the bridge forwarding table, never the station's own or another station's MAC, a group address, or a permanent, self or static (administrator-created) entry. `online_source` is `hostapd` when `online` is hostapd's authorised flag from the latest successful `all_sta` call and `log` when it is derived from the connect and disconnect events; the manager forgets the `all_sta` answer whenever the call fails or hostapd_cli is unusable, so a stale flag is never kept. Addresses come from unexpired DHCP leases and IPv4 neighbour entries (stale neighbour entries included); the conflict flag is computed over all of them, including MACs that are behind no station, is shown on every claimant and is never resolved. A lease or neighbour entry for a MAC that is behind no station port is not attributed to any station. `state.sh` re-validates every MAC and IPv4 address and drops what is not well formed. `/diagnostics` and `/status.json` carry the same station data (the redactor removes secrets, not addresses). `diagnostics` is served only by `/diagnostics`.

### 5.2 Status service (`rootfs/usr/lib/halow/status/`, `rootfs/etc/services.d/status/`)

Python 3 standard library only. `GET` only: any other method is refused with 405. Routes `/` (HTML page, no external resources), `/status.json` (snapshot without `diagnostics`, plus a computed `stale` boolean from `updated_at` and `HALOW_STATUS_STALE_AFTER_S`), `/diagnostics` (redacted, with `diagnostics`), `/health` (answers `ok` to the allowed peer only; the manager does not use it). Accepts connections only from `HALOW_STATUS_ALLOW_FROM`; binds `HALOW_STATUS_BIND`. Reads the snapshot read-only; never receives the Supervisor token. Redacts again on output. Handles a missing, partial or malformed snapshot by showing `STATUS_STALE` or "starting". The page shows when a backup channel is in use. The validation fields stay in the snapshot but the page does not display them. The launcher waits for `HALOW_RUN_READY_FILE` (it never writes under the run directory before that file exists), reads the Ingress port once as root, verifies that the token files are not readable by `HALOW_STATUS_USER` (refuses to start the server otherwise), prepares the liveness directory (always `/run/halow-status`, the file `heartbeat` in it: an override of the path is honoured only when `HALOW_STATUS_TEST_MODE=1`, never in production, and even then only for a directory named `halow-status` and a file named `heartbeat`, never `/`, `/run`, `/tmp` or `HALOW_RUN_DIR`; a link or a non-directory at the path is refused; the directory is removed with `rm -rf` (which does not follow links), created again, given the owner `HALOW_STATUS_USER` and mode 0700, and owner, mode and emptiness are checked, so nothing an earlier life left there (a counter, a directory, a FIFO, a link) survives or blocks the start), writes the port to `HALOW_STATUS_PORT_FILE` (0644), then drops to `HALOW_STATUS_USER` with `s6-setuidgid` and passes only the port, the bind address, the allowed peer, the snapshot path, the stale threshold and the counter path. The server publishes the liveness counter from `StatusServer.service_actions()`, which `serve_forever` calls on every pass of the accept loop (not from a separate timer thread, which would keep running while the accept loop is hung): the first value (1) before the first connection is accepted, then +1 at most every 5 s (`HEARTBEAT_INTERVAL_S`), written to `<file>.tmp` (mode 0600, no symlink followed) and renamed over the counter file; a write that fails is reported once on stderr and never stops the server. The default peer allow list is exactly `172.30.32.2` (`HALOW_STATUS_ALLOW_FROM`); the manager's checks never need another peer, so none is added. The peer address is checked when the connection is accepted, before the request is parsed, and concurrent connections are capped.

Rules: AU offers **1, 2, 4 and 8 MHz**, each marked `implemented` (an internal marker in `radio_profiles.psv`, not a validation record). Manual mode requires a channel valid for the region and width; automatic mode ignores any channel. Candidate fallbacks are marked `candidate`. Operating class, scheme and primary-channel settings are internal.

Channelisation: the product supports one scheme per region, and for AU that is **IEEE 802.11-2024** (the dot11ah module is loaded with `channelization_scheme=2`; operating classes 50, 51, 52 and 53 for 1, 2, 4 and 8 MHz; channels 28 to 50 as listed in `radio_profiles.psv`). There is no customer-facing scheme selector. The scheme is a column of the region row, and the channel sets, operating classes and fallback candidates are rows of the same table, so another scheme would be a new set of rows and a different region row value, not a change to the code that renders, validates or starts the radio; none is provided, and the AU channel numbers of one scheme are not valid in another. hostapd parses the AU operating classes 48 to 53 under the scheme it records as REVmf and has no operating-class value that selects its 2024 data, but when the access point starts it asks the driver for its scheme (the access point does not start if that query fails) and switches to it; its channel tables are identical to its 2024 tables for channels 28 to 50 (the comments in `radio_profiles.psv` give the evidence; only the parse step is exercised off-device). The scheme-2 selection, the driver scheme query, automatic channel selection and real client association on the AU 8 MHz channels 35 and 43 were exercised in live tests on one Home Assistant Green with two client types (with scheme 2 a firmware that does not handle the command makes the driver fail, and the add-on fails closed in an attention state).

Access point program: `hostapd_s1g` and `hostapd_cli_s1g` are built from the Morse Micro `hostap` tag `mm8108-2.1.0`, the release that matches the bundled driver and firmware (an earlier build paired a `hostap` build from the older `1.17.9` line with this driver). This `hostapd_s1g` talks to the driver over nl80211 vendor commands (`CONFIG_DRIVER_NL80211_MORSE`, with `CONFIG_MORSE_5GHZ_MAPPED` for the mapped channel handling), so it runs no helper program: `halow_start_hostapd` starts it with the environment it inherited and does not touch `PATH`, and no separate helper program is shipped. The configuration keys the renderer writes, the `status` S1G fields the add-on parses and the automatic-channel-selection events it waits for are the same in both lines. At 8 MHz on channel 43 an earlier build with the older line failed to let clients join. Source analysis (reading the hostap source and running its probe-request filter against a model of the driver's frequency reporting) indicates that the older line drops probe requests on that channel when paired with this driver, and that the release now shipped does not. Beacons in this stack never carry the security parameters (the driver clears the RSN elements from beacons unless `rsn_beacon_mode` is set, and it defaults to 0), so a client relies on probe responses to learn them; a dropped probe request therefore looks like a beacon without security information. This is a source-level finding (the add-on's profile and renderer are tested off-device for every width and for channels 35 and 43), not by itself a device result. On one Green, 8 MHz channel 43 then worked with this release in a longer test and in a bounded start-up check of the final files with one client (limited evidence).

### 5.4 `guard.sh` and `adapter.sh`

```
halow_guard_check                  0 supported; 1 unsupported (HALOW_GUARD_REASON set); 2 undeterminable (treated as unsupported: fail closed)
halow_guard_report                 prints key=value lines for diagnostics
halow_adapter_scan                 sets HALOW_ADAPTER_COUNT, HALOW_ADAPTER_SYSFS, HALOW_ADAPTER_UNRECOGNISED_COUNT

halow_adapter_netdev_wait <timeout_s>
halow_adapter_present              0 if the same adapter is still present
```

The guard is read-only. It runs before any host change except two that precede it in every start: the run-directory tmpfs mount and reconcile undoing this add-on's own residue from an earlier run (§ 4 steps 1–2); nothing else (firewall, modules, firmware, bridge, access point) happens before it passes. Its path overrides (`HALOW_GUARD_MANIFEST`, `HALOW_UNAME_RELEASE`, `HALOW_UNAME_VERSION`, `HALOW_PROC_VERSION`, `HALOW_PROC_CONFIG_GZ`, `HALOW_MODULES_BASE`, `HALOW_SYS_MODULE_DIR`) are honoured only when `HALOW_GUARD_TEST_MODE=1`; otherwise the production paths and `uname` are used. It checks the **exact host-module identity** against `rootfs/usr/share/halow/guard_manifest.psv`, in this order: the manifest is complete and well formed; the kernel release (`uname -r`) is listed; the build string (`uname -v`) matches; `/proc/version` equals the recorded banner; the SHA-256 of the decompressed `/proc/config.gz` matches; the bundled `morse.ko` and `dot11ah.ko` carry the release's vermagic and recorded srcversion; then for each of the host's `cfg80211`, `mac80211` and `libarc4`: the file the module loader would use (`modinfo -b <base> -k <release> -F filename`) is the recorded path, exactly one `<module>.ko*` exists in the release's module tree (symbolic links to directories are followed), the recorded path is a regular file (a symbolic link is refused), its SHA-256 as stored equals the recorded official value, and its vermagic matches; finally, the loaded-module directory must be readable and list other modules (missing, unreadable or empty is undeterminable, never "not loaded"), and for any of the three already loaded, `/sys/module/<name>/taint` is empty and, where its build-id note is readable, the build-id matches. Anything missing, unreadable or malformed is a refusal (2), any difference is a refusal (1); both raise `UNSUPPORTED_KERNEL`. The recorded values are the official files of the one supported Home Assistant OS release, taken from its published disk image and its signed update bundle (which agree); each official build signs its modules with its own generated key, so the file hash identifies that build. **What it establishes:** the exact official module files of the supported release and the running kernel's banner and configuration. **What it cannot establish:** the dependency chain `modprobe` would load is not inspected separately (the file is resolved through the same module index, and the report records the chain as unverified); protection against a hostile root user on the host or a kernel deliberately forged to mimic these strings. A different Home Assistant OS release is refused until its values are added. *Unverified on the target device:* what `/lib/modules` contains inside the container at run time, `/proc/config.gz`, the sysfs taint and build-id notes, and `uname -v` inside the container.

`ipv6.sh` (IPv6 is switched off on the add-on's own interfaces; the IPv6 filter chains are the second control):

```
halow_ipv6_disable <iface>        records the interface's current net.ipv6.conf.<iface>.disable_ipv6 value in the ownership
                                  marker ipv6_<iface> BEFORE writing 1 to $HALOW_PROC_SYS_DIR/net/ipv6/conf/<iface>/disable_ipv6,
                                  reads it back; 0 verified, 1 when it cannot be written or verified, 2 (INCOMPLETE, stronger) when a temporary
                                  writable mount on the switch is held or not confirmed removed (a held bracket record or listed
                                  mount is cleaned up and verified first, so an already-written value never hides one). The write is made inside a
                                  bracket on that one file (below); "all", "default", "." and ".." are refused by name first
halow_ipv6_restore_all            restores every ipv6_* marker's recorded value (an interface that no longer exists counts as
                                  restored), clears each marker only after confirmation; 1 if any is unconfirmed
halow_ipv6_present                0 if any ipv6_* marker or ipv6br_* bracket record is held
```

The write bracket. The container is not privileged, so Docker mounts `/proc/sys` read-only for it and a plain write to a `disable_ipv6` file fails with `EROFS`. Each write (the disable, and the restore of a recorded value) is therefore made as: `mount -o bind F F` (a container-local bind mount of that exact file), `mount -o remount,bind,rw F` (flips only that mount; the proc superblock, `/proc/sys`, every other file and interface, `all` and `default` stay read-only), the write, then `mount -o remount,bind,ro F` and `umount F`. The bracket record `ipv6br_<iface>` (content `ro` or `rw`: whether a plain write was refused before) is written before the first mount and cleared only after the cleanup is verified: the mount table (`/proc/self/mountinfo`) no longer lists the exact path and, for `ro`, a write is refused again. Leftovers (a manager killed between the steps) are looked for in the mount table itself, never only in the record, before every bracket and in every `halow_ipv6_restore_all` (so in rollback and reconcile): every mount stacked on a `disable_ipv6` path is made read-only and unmounted until none is listed. A cleanup that cannot be verified is reported as INCOMPLETE, keeps the record, and rollback lists the record as residual ownership. Not yet validated on the target device.

Callers and failure classes. A return of 2 from `halow_ipv6_disable` is stronger than 1: a temporary writable mount may be left, so the manager fails closed (`BACKEND_FAILED`, naming that the mount could not be confirmed removed) and the bridge backend refuses the station and takes its port out of the bridge; neither falls back to the firewall alone. A return of 1 (the write or the mount was refused, the value could not be read) keeps the documented fallback: when the IPv6 filter chains are verified in force the run continues with a warning and the diagnostic entry `ipv6_<iface>` ("IPv6 is NOT off on the interface ...; held by the IPv6 filter chains only"; the per-station path has no status channel and logs the warning only). A stale mount that nobody recorded and whose cleanup cannot be verified gets a bracket record before the failure, so rollback lists it as residual ownership; a restore failure that no record accounts for while the mount table is readable shows in the rollback residue as `ipv6-switch-mount`; an unreadable mount table with nothing listed and nothing recorded is only logged (the set side already fails closed), so it cannot refuse forever. An interface that is renamed keeps its sysctl value; the record under the old name finds that the old name no longer exists and is cleared (documented, not a safety issue).

Environment overrides. `HALOW_PROC_SYS_DIR`, `HALOW_PROC_MOUNTINFO` and `HALOW_NFT` are plain environment variables like every other overridable path and binary here (`HALOW_IPTABLES`, `HALOW_TIMEOUT_CMD`, ...); production code does not ignore them. The container environment is set by the Supervisor from the add-on's own configuration, not by a client. A hostile environment that set them could point the verification at files of its choosing (verification would then fail open); this residual is accepted and not mitigated here.

Backend `bridge` satisfies `backend.sh`'s contract. `configure` takes `bridge= subnet= dhcp_start= dhcp_end= uplink= parent= max_stations=`; `attach bridge <name>` isolates the parent port, assigns the gateway address to the bridge, starts dnsmasq bound to the bridge (lease file in `HALOW_LEASE_DIR`, persistent; the configuration says `quiet-dhcp`, so routine DHCP transactions are not written to the add-on log, while errors and important messages still are, for example a pool-exhaustion message that names the client MAC) and installs the NAT chain through `halow_fw_install_nat`; `station_added <port> <mac>` makes sure the port is a bridge member with isolation on, switches IPv6 off on a per-station interface (`halow_ipv6_disable`), and (for a per-station interface) re-checks NetworkManager under the key `nm_unmanaged_wds_<iface>`; a station refused for the station limit has its per-station port released. A hard failure sets `HALOW_BB_FAIL_KIND` to `nm` (NetworkManager) or `other`. `teardown` removes DHCP and the NAT chain. Ownership keys: `net_bridge_addr net_dnsmasq fw_nat` (the bridge itself is core-owned: `net_bridge`). `halow_backend_register_default` registers `bridge`. The earlier routed/NAT backend stays in the tree for the contract tests only.

`stations.sh` serves **both** station kinds: a station that is announced with its own per-station interface (four-address client) uses that port; a station for which no interface appears within `HALOW_ST_ORDINARY_WAIT_S` (default 3 s) is an **ordinary** station on the parent port. The bridge is attached at start (not on the first station). `halow_stations_snapshot_lines` prints the station records described under the snapshot contract (§ 5.1): an ordinary station is its own device (addresses from an unexpired lease or a neighbour entry for its MAC); a four-address station has zero or more devices, every MAC learned behind its port (excluding its own MAC), each with every address a lease or neighbour entry gives it, and "unknown" only when none does. The hostapd log slice is bounded (rotation without losing or replaying events).

## 6. Ownership keys

Core: `firmware_main firmware_bcf firmware_dir fw_search_path nm_unmanaged_parent nm_unmanaged_bridge nm_unmanaged_wds_<iface> module_intent_<name> module_dot11ah module_mac80211 module_morse net_bridge fw_filter fw_created_input4 fw_created_input6 hostapd_process ipv6_<iface> ipv6br_<iface>`. Backend (`bridge`): `net_bridge_addr net_dnsmasq fw_nat`. Rollback asks the registered backend for its keys and also treats every `nm_unmanaged_wds*`, `ipv6_*` and `ipv6br_*` key as owned. `fw_created_input4`/`fw_created_input6` record that this add-on created the (empty) `INPUT` base chain of the IPv4/IPv6 filter table; they are released with the filter chains and dropped, never acted on, after a reboot.

## 7. Radio configuration model

`region`, `radio_mode` (`automatic` default, `manual`), `bandwidth` (customer-selected; development default 1 MHz) and `channel` (list; default `auto` = none chosen; used only in manual mode; `auto` is read as an absent channel) are always present in the static options schema. Automatic mode runs channel selection within the configured bandwidth at every add-on/access-point start; the add-on ignores any saved `channel` (Home Assistant itself still refuses a value outside the schema list). Manual mode requires a channel valid for the region and bandwidth; an invalid choice is a configuration error and never falls back. Channel selection failure or timeout starts the fallback channel for the bandwidth with a prominent advisory, never reports it as a successful automatic selection, never stores it as a selected result, and retries selection at the next start.

## 8. What is not claimed

Evidence is limited to one Home Assistant Green and the clients used in testing. Not established on a device: that the firewall hook positions survive a Docker restart, behavior under many clients or heavy load, every bandwidth and fallback channel with real clients (the records say which were exercised), and the exact release candidate running with the USB-C adapter (the USB-C adapter was used with the Home Assistant Green in earlier testing; the release candidate was tested with the USB-A adapter). The AppArmor profile ran in enforce mode in earlier live sessions on Home Assistant OS 18.3 (see `apparmor.txt`; an enforce record on 18.4 specifically is not recorded); its mount rules were derived from BusyBox `mount` traced under `qemu-aarch64 -strace`. The manager's direct checks of the status service (s6 state and process identity, the listening port in the kernel's TCP table, the liveness counter) and the AppArmor rules for the counter directory are verified off-device only (fakes in the kernel's formats, a real server process, the real `/proc` and loopback sockets): that a healthy status service passes them on the device, and is not restarted needlessly, is unverified; so is whether the kernel on the Green lists the status server's listener as the checks expect. The token restriction is shown off-device only, under the image's real s6-overlay start-up. Release-gate matters (source offer and archive, redistribution rights, licence texts, stripped rebuilt binaries, complete image provenance) are outside this document.
